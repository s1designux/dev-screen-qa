# 다음 조각 ② — 토큰·컴포넌트 규정 대조 (착수 전)

이 문서만 읽으면 새 세션에서 바로 이어서 할 수 있게 적는다. **아직 구현하지 않았다.**
앞 조각(① 시안↔개발 값 대조)은 끝났다 — `valueqa/`, 커밋 `60fbeaf`.

---

## 왜 이 조각이 필요한가

① 은 "**이 화면의 시안**과 개발이 같은가"만 본다. 그런데 river 가 가장 중요하게 보는 것은 다른 것이다:

> "우리 회사에서 정한 **토큰값과 컴포넌트 규정**을 그대로 잘 지켰는지" (river 2026-09-14)

시안과 픽셀이 같아도 **토큰 밖의 색·크기**면 규정 위반이고, 반대로 시안 자체가 규정을 벗어났을 수도 있다.
그래서 화면 1:1 대조 위에 **'규정'이라는 제3의 기준자**가 하나 더 있어야 한다.

또 하나. ① 의 지시서는 "이 버튼 색을 바꾸세요"라고만 말할 수 있다. 그런데 개발이 공통 컴포넌트를
고치면 다른 화면까지 바뀐다. **"이건 이 화면만의 문제가 아니라 버튼 규격 자체"** 라고 말해 줄 수 있어야
개발이 안전하게 고친다. 그 말을 만들어 주는 것이 이 조각이다.

---

## 정해진 것 (재논의하지 않는다)

- **정본은 `https://github.com/s1designux/S1-UX-DESIGN-with-AI`** (공개 저장소, river 2026-09-14).
- **아직 정리 중이라 시시각각 바뀐다.** → 복사해 두지 말고 **검수할 때마다 받아오고, 본 판(커밋 SHA)을
  지시서에 적는다.** 낡은 사본으로 판정하면 틀린 지적이 된다.
- **검수 PC는 깃허브 내려받기가 된다**(올리기만 막힘). 파일로 들여오는 통로는 필요 없다.
- 순서: ①값 대조(완료) → **②토큰·컴포넌트 규정(이 조각)** → ③흐름 검수.
- **화면끼리 일관성 검사는 하지 않는다** — 시안 대조가 되면 저절로 정리된다(river 제외 결정).
- 결과물은 '보는 문서'가 아니라 **'고치는 문서'**. ① 의 지시서(`valueqa/fixdoc.py`)에 얹는다.
- 고칠 자리는 **개발 화면 기준**(`#id`·CSS 선택자). 디자인 레이어 이름은 보조.
- **자동으로 확정하지 않는다.** 후보만 만든다(CLAUDE.md 2번-2).

## 착수하면 맨 먼저 할 것 (5분)

내부망 PC에서 **정본을 받아올 수 있는지** 확인한다. 깃허브 화면은 열려도 파일 내려받는 주소가
따로 막혀 있는 경우가 있다. 세 길 중 되는 것을 쓰면 된다.

```
curl -sI https://raw.githubusercontent.com/s1designux/S1-UX-DESIGN-with-AI/main/registry/index.json
curl -sI https://codeload.github.com/s1designux/S1-UX-DESIGN-with-AI/tar.gz/refs/heads/main
gh api repos/s1designux/S1-UX-DESIGN-with-AI/contents/registry/index.json   # gh 가 깔려 있으면
```

셋 다 막혀 있으면 거기서 멈추고 river 에게 알린다 (파일로 들여오는 통로를 새로 정해야 한다).

## 정본에 무엇이 들어 있나 (2026-09-14 실제 확인)

기계가 읽을 수 있는 모양으로 이미 정리돼 있다. 새로 만들 것이 없다.

| 무엇 | 어디 | 모양 |
|---|---|---|
| 색·간격·모서리·글꼴 토큰 | `registry/tokens/foundation.*.json` · `semantic.*.json` | `{value, cssVar, status}` — 예: `"white": {"value":"#FFFFFF","cssVar":"--color-base-white","status":"stable"}` |
| 모든 토큰의 실제 CSS | `assets/css/tokens.css` | `--color-gray-100: #E9E9E9;` (자동 생성물, 정본) |
| 컴포넌트 규격 | `registry/components/*.json` | variants(primary·secondary·blue-line) · pcSize(md 44 / xsm 34 / xxsm 28) · state · 쓰는 토큰 목록 · doDont(금지 사항) |
| 컴포넌트 ↔ 웹 클래스 | `registry/governance/component-geometry-map.json` | `"Button": {"prefixes":["s1-btn"]}` — **개발 화면에서 컴포넌트를 알아보는 열쇠** |
| 그만 쓰는 토큰 | `registry/tokens/deprecated-tokens.json` · `governance/token-exceptions.json` | 예외·폐지 목록 |
| 전체 색인 | `registry/index.json` | 위 파일들이 어디 있는지 |

주의할 것 두 가지:
- `registry/tokens/component.tokens.json` 은 **은퇴**했다(2026-07-02). 쓰지 말 것. `index.json` 이 그렇게 적어 두었다.
- `registry/tokens/legacy/` 는 옛 스냅샷이다. 현행 정본 CSS 는 `assets/css/tokens.css`.

## 이 조각이 하는 일 — 세 가지 판정

① 이 뽑아 놓은 개발 값(`valueqa` 가 쓰는 `*.값.json`)에 대고 본다.

1. **토큰 밖의 값인가** — 개발 화면의 색·글자크기·모서리·테두리가 토큰 목록 안에 있나.
   없으면 "토큰 밖 값" 후보. **가장 가까운 토큰을 함께 제안한다**(`#0073CF` → `--color-brand-blue #0072CE`).
2. **컴포넌트 규격을 지켰나** — 클래스 접두사(`s1-btn` 등)로 그 요소가 어느 컴포넌트인지 알아낸 뒤,
   그 컴포넌트의 정본 규격(크기 44/34/28, 허용 variant, 상태별 토큰)과 맞는지 본다.
   폐지된 variant(danger·ghost)를 쓰면 그것도 후보.
3. **시안 자체가 규정을 벗어났나** — ① 에서 '시안 값'이 토큰 밖이면 개발이 아니라 **디자이너에게** 간다.
   지시서에 섞지 말고 따로 모은다.

## 지시서에 어떻게 얹나

`valueqa/fixdoc.py` 에 장을 더한다. **기존 장을 흔들지 않는다** — ① 의 자가검사 8번이 잠그고 있다.

- 새 장 **"규정에 어긋난 값"** — 항목 번호 체계(`{화면키}-{번호}`)를 그대로 쓴다.
  바꿀 값을 **토큰 이름으로** 적는다: `background-color: var(--color-brand-blue)` /* #0072CE */
- 새 장 **"컴포넌트 규격"** — "이 버튼은 PC md(44px) 규격입니다. 지금 41px 입니다" 식으로.
  ⚠ **공통 컴포넌트라 다른 화면도 함께 바뀝니다** 를 이 장에 붙인다(① 의 쓰는 법 3번과 이어진다).
- 문서 머리에 **본 정본 판**을 적는다: `디자인 정본 a1b2c3d (2026-09-14 받음)`.
  `지시서()` 에 이미 `정본커밋` 인자가 있다 — 채우기만 하면 된다.
- 시안이 규정을 벗어난 것은 **디자이너용 따로 목록**으로. 개발 지시서에 섞으면 개발이 헷갈린다.

## 지켜야 할 것

- 자동으로 확정하지 않는다. 신뢰도와 함께 후보만.
- 정본을 저장소 안에 복사해 두지 않는다. 받아 쓰고, 본 판만 적는다.
- 화면마다 사람이 설정하게 만들지 않는다 — 기본값(4계층 상속, CLAUDE.md 8번)으로 흡수한다.
- ① 의 숫자를 흔들지 않는다. 고치고 나서 **반드시 둘 다** 돌린다:
  `python3 -m valueqa.selftest` 와 `npm test`.
- 앱·PC S/W 길(그림 대조)은 건드리지 않는다.

## 검증 기준 (이 조각이 끝났다고 말하려면)

1. 정본을 받아와 토큰 목록을 세운다 — 색·간격·모서리·글꼴 몇 개인지 숫자로 보인다.
2. 일부러 토큰 밖 색을 넣은 시험 화면에서 **그 색만** 잡고, 가장 가까운 토큰을 맞게 제안한다.
3. 토큰 안의 값만 쓴 화면에서는 **후보가 0** 이다(헛것 없음).
4. 버튼 높이를 44 → 41 로 틀어 놓은 시험 화면에서 컴포넌트 규격 어긋남을 잡는다.
5. `valueqa.selftest` 와 `npm test` 가 그대로 통과한다.

시험 화면은 `validation/dev.html` 을 복제해 만든다(이미 헤드리스로 값을 잴 수 있다).

## 착수 때 river 에게 물을 것

- **개발 화면이 정말 `s1-btn` 같은 클래스를 쓰나?** `component-geometry-map.json` 의 접두사는
  디자인 시스템 **전시 페이지** 기준이다. 실제 서비스 화면이 다른 이름을 쓰면 컴포넌트를 알아보는
  다른 길(요소 모양·크기로 추측)이 필요하다. **이것이 이 조각의 가장 큰 미지수다.**
- 토큰 밖 값을 얼마나 엄격히 볼까 — 완전히 같아야 하나, 아주 가까우면(1~2 차이) 넘어갈까.
- 처음 검증은 어느 화면으로 — 퍼블리싱 화면(오프라인)인지 실제 개발 사이트인지. (① 에서도 아직 안 정했다)
