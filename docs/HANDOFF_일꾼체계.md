## 2. 확정된 계획 (2판)

### 세 자리 + 프로그램
| 자리 | 하는 일 | 절대 안 하는 일 |
|---|---|---|
| 운영 AI | river 창구. 규칙 파악·근거 수집·제안·보류 사유 관리·보고 한 장 | 코드 수정, 숫자 직접 적기 |

| 프로그램 | 회귀 실행·공식 성적 적기·문서 생성·백업/자료 목록 점검·**문지기** | — |

### 규칙 한 건이 가는 길
제안 기록 → **[river] 범위·기준 승인(승인번호)** → 구현 → 공식 측정(프로그램) → 독립 검토(떨어지면 구현으로, 최대 2번) → 문지기 → **[river] 적용 승인**

문지기: 승인번호 없음 → 불가 / 공식 성적 없음 → 불가 / 측정 뒤 코드·설정 바뀜 → 재측정. 커밋 전 검사(hook)만으로 됐다고 보지 않는다(우회 가능).

### 시험지 보호
- 정답·재현 세트·측정 도구·통과 기준은 구현 AI가 못 여는 자리에. 결과 쓰는 칸만 분리.
- 양면 시험: 규칙마다 "없애도 되는 후보" + "비슷하지만 남아야 하는 오류" 함께.
- 공식 숫자는 프로그램만 적는다. 빠지거나 실행 오류면 "통과"가 아니라 **판정 불가**.
- 지금까지의 647 · 329 · 316 · 457 은 재현 조건이 제각각 → **참고 기록**. 출발점은 다시 잰다.

### 장부 셋 (저장소 안 `규칙장부/` 파일 · 포털 운영 데이터는 지금처럼 DB · 같은 정보를 두 곳에서 고치지 않음)
- 규칙 장부: **사건 하나 = 한 줄**(등록→승인→검증 실패→반영). 현재 상태는 이력에서 계산. 제안번호 ≠ 규칙번호. 규칙번호는 코드 위치·계층·설정과 연결.
- 측정 장부: 한 번 재기 = 한 줄. 엔진 지문 + 4계층 설정 + 화면·요소 목록 + 정답 + 도구 버전의 지문 + 원본 결과 파일. 전후는 같은 조건끼리만.
- 자료 목록: 재현 세트·백업·옛것마다 정본 여부·위치·치우는 조건. 치우기는 조건 충족을 프로그램이 확인한 것만.

### 제안 접수 기준 ("근거 화면 둘 이상" 폐기)
| 적용 범위 | 확인할 근거 |
|---|---|
| 요소·화면 예외 | 그 사례·정확한 대상·재적용 멈출 조건 |
| 서비스 공통 | 서로 다른 화면·조건에서 같은 원인(같은 양식 복제본은 근거 아님) |
| 시스템 기본 | PC/모바일/앱 영향 + 잘못 빠질 반례 |

### 순서
① 정본 DB 확정 + 복원 시험 → ② 기준 성적 확정(같은 입력·설정) + 시험지 분리 + 양면 시험 틀 + 문지기 → ③ 장부 채우기 + 세 자리 정의(`.claude/agents/`, `.claude/skills/`) → ④ 시범 한 바퀴: 제안 #1(표 항목 이름 고정) → ⑤ 대기열 0-1부터 이 길로.
④에서 함께 시험: 승인 없는 변경·오래된 성적 재사용·정답 파일 손대기가 **실제로 막히는지**. 실패·중단도 기록.
